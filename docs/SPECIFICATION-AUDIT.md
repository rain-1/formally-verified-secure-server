# Audit of the server's formal specifications

Baseline reviewed at commit `e0cd4d2d081cdc16af7304dac3746484c33b92fa`. This audit compares the published claims with the public contracts, the code that composes them, and the public Aristotle specifications. The proof inventory tracks subsequent additions. [README](../README.md#verification-progress) · [Proof inventory](PROOFS.md) · [Trust assumptions](TRUST.md)

The strongest results constrain actual bytes. HTTP normalization and lookup identify the entry a request can select in a supplied table. TLS server-flight composition ties the emitted records to the transcript and the keys retained for the next step. The extracted C result for client Finished then supplies a meaningful authentication condition on the transition to application keys. These are worth keeping. The missing assurance is that a real connection exercises those guarantees together, from startup and ingress through the exact response sent. The milestone percentages measure roadmap completion. They give no coverage measure for that connection-level property. [HTTP routing](../src/Http.Server.fst#L919) · [Server flight](../src/Tls.Server.fst#L425) · [Client Finished evidence](evidence/aristotle-client-finished.md)

## HTTP request to response

**The route property is meaningful over an immutable table.** Normalization has a concrete byte specification independent of the buffer operations. A routed hit selects an in-bounds entry with the normalized key and the expected body offset. A routed miss means the path is outside the lexical policy or the key is absent among in-bounds entries. This is enough to rule out selection of an unrelated table entry on a reported hit, given a table with unique keys. It places no requirement on what the loader put at that key. [Path model](../src/Http.Spec.fst#L40) · [Lookup](../src/Http.Core.fst#L105) · [Routing contract](../src/Http.Server.fst#L919)

**The caller needs one contract that starts with request bytes and ends with response bytes.** The parser guarantees a valid header section at the reported offsets on acceptance. The request-line checks in the implementation identify GET or HEAD and the HTTP version, but the parser postcondition exposes neither the method's wire meaning nor an exact request-line parse. The header builder separately proves the exact serialization for its arguments. At `handle`, the public postcondition provides a write frame, bounds for reported responses, and the conditional routing predicate. On a hit, body length may be the whole entry or zero, independently of the request method in that predicate. The source passes the entry length to the serializer and chooses zero body bytes for HEAD. A caller needs that relation in the contract, including the corresponding status, serialized header, consumption, and close behavior. [Parser contract and implementation](../src/Http.Parse.fst#L405) · [Response construction](../src/Http.Server.fst#L1080) · [Public handler](../src/Http.Server.fst#L1152) · [HEAD semantics, RFC 9110 §9.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2)

**Some acceptance choices belong in the policy before proving it.** The current header predicate checks one field named `Host`, with value syntax shared by other headers. An authority syntax or host-to-site relationship would require its own condition. The no-body rule allows repeated `Content-Length` fields when each is zero. The substring-based close rule is intentional and documented. The stated 400/405/431 policy should distinguish request syntax and framing errors from a path outside the site's lexical policy, which the route can map to 404. Decide these behaviors explicitly for this single-site origin. A pure parser model should describe the intended first request and its suffix for every byte prefix, with a stable error classification where clients rely on it. [Header predicate](../src/Http.Parse.fst#L112) · [404 branch](../src/Http.Server.fst#L1097) · [HTTP policy](POLICY.md#http) · [HTTP message framing, RFC 9112 §6](https://www.rfc-editor.org/rfc/rfc9112.html#section-6)

**Content provenance is a startup property.** The loader walks from an opened directory descriptor, opens children relative to it with `O_NOFOLLOW`, and checks regular-file metadata on the descriptor it reads. Its skip rules and size limits define which content can enter the table. A reasonable initial theorem is over a stable, operator-controlled tree and an already resolved root descriptor. It should establish unique keys, bounds for every entry, and that each stored body equals the bytes read from the corresponding permitted regular file. Decide how mounts, hard links, the configured root path, and skipped entries fit the policy before claiming a stronger filesystem boundary or a complete snapshot. A coherent snapshot under concurrent mutation would need a different environment contract or loader design. [Site loader](../shell/src/site.rs#L17) · [Opened file checks and table population](../shell/src/site.rs#L57) · [Descriptor-relative open](../shell/src/site.rs#L149)

## TLS hello to authenticated application data

**The server-flight proof establishes byte and state consistency.** Given a successful `do_ch`, the plaintext ServerHello and the plaintext protected by the next record are the bytes in the transcript. The proof connects their key schedule, the stored hash through server Finished, and the key material carried into the next phase. The existential hello witnesses establish serialization and derivation for a session ID, suite, public share, and shared secret. A negotiation theorem must further identify those witnesses from the actual offers, random bytes, and group operation. At the audited commit, the F* parser reported abstract ClientHello body validity and the outer grammar established framing. Those statements leave extension semantics, suite choice, session ID echo, key-share selection, and the ALPN decision as separate obligations. At the audited commit, the public `run_ch` contract retained result bounds from `do_ch`. The public input entry point needed an explicit link back to the flight theorem. [Hello witnesses](../src/Tls.Server.fst#L256) · [Handshake composition](../src/Tls.Server.fst#L425) · [ClientHello grammar](../spec/ClientHello.3d) · [Parser boundary](../src/Tls.Hello.fst#L428) · [Public handshake caller](../src/Tls.Conn.fst#L221) · [TLS key share, RFC 8446 §4.2.8](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.8)

**CertificateVerify has meaningful encoding and input provenance.** The C evidence connects the actual bytes returned by the signer to the canonical DER bytes in the flight. The signer receives the input derived from the right transcript. A peer-authentication statement also needs the raw signature to verify under the leaf public key and the leaf to be the configured server credential. F* uses a memory-level signing contract, and the public Aristotle model treats signing as an external relation. Credential preparation and operator trust in the issuer, name, validity period, and key custody are distinct from the code-level key-match and signature obligations. The server does not request client certificates, so Finished establishes key and transcript confirmation, not the client's identity. [Flight signature model](../src/Tls.Spec.fst#L164) · [CertificateVerify evidence](evidence/aristotle-certverify-der.md) · [Credential loading](../shell/src/main.rs#L107) · [TLS Finished, RFC 8446 §4.4.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.4)

**Client Finished is a necessary-condition theorem with a useful failure invariant.** The C proof starts with a phase-1 state and says that a transition requires a complete, authenticated Finished for its stored transcript and secret. A transition consumes the first record, installs the expected application read keys and IV, and resets the sequence. Incomplete input and rejected record authentication have separate guarantees. The Lean AEAD assumptions say that successful C decryption agrees with the model. They permit an implementation that always rejects, which would satisfy the transition implication without connecting a valid peer. A progress theorem needs the converse opening contract on valid records and must start from a reachable phase-1 state produced by the actual flight. Today that handoff is supported by matching source and human review across F* and Aristotle. The service retains its implementation proof, while the public statements and contracts build locally. [Client Finished evidence and public Lean files](evidence/aristotle-client-finished.md) · [Public F* input contract](../src/Tls.Conn.fst#L495)

**The supported handshake needs a wire-level definition.** The phase-0 implementation expects the complete ClientHello in one TLS record and caps its handshake body at 4,096 bytes. Phase 1 likewise expects the complete Finished in one opened record. TCP segmentation and TLS handshake fragmentation are separate. A progress theorem for the current code should name the single-record premise and the credential and buffer limits. A progress theorem for clients that use TLS handshake fragmentation would need record-spanning reassembly. [ClientHello dispatch](../src/Tls.Conn.fst#L269) · [Finished dispatch](../src/Tls.Conn.fst#L355) · [TLS record framing, RFC 8446 §5.1](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.1)

**At the audited commit, record helpers constrained the data closely and the entry points exposed mainly lengths and phases.** `send_rec` proves exact modeled wire bytes with the pre-call write key, IV and sequence. `open_rec` identifies the model plaintext, its type byte, and trailing padding and relates successful opening to sequence advancement. The public `seal_app` postcondition gave a length or zero. The public `input` postcondition bounded its results and limited application delivery to phase 2. The relation between delivered bytes and the authenticated plaintext prefix was still open. A usable stream theorem must also specify which record was consumed, how an incomplete suffix is retained, what is written on rejection, and which close events have authenticated provenance. The code has a separate phase-2 disposition for a plaintext outer Alert. Decide how the API should distinguish transport termination from authenticated TLS shutdown before specifying closure. [Record sealing](../src/Tls.State.fst#L157) · [Record opening](../src/Tls.Conn.fst#L125) · [Application entry points](../src/Tls.Conn.fst#L413) · [TLS record protection, RFC 8446 §5.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.2)

**Nonce arithmetic is a prerequisite for a key-usage invariant.** The nonce and increment proofs are useful locally. A reachable-state theorem should show that each direction and key epoch uses each sequence at most once, and that enforcing a suite-specific record budget prevents further protected traffic after exhaustion. The current sequence guard checks the two high bytes and the policy omits KeyUpdate. That ceiling alone permits many more records than the AES-GCM usage guidance for full-size records. A separate deployment bound or a checked budget with defined connection shutdown is needed for a theorem claiming the corresponding AEAD security margin. Count usage in the model for both directions, including failed opening attempts where the chosen security bound requires it. [Sequence guard](../src/Tls.Crypto.fst#L190) · [TLS policy](POLICY.md#tls) · [TLS key-usage limits, RFC 8446 §5.5](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.5)

## Theorems to add

The statements below are proposals. Order reflects the ability to reuse the existing proofs and what each new result would let a caller conclude. The first two can proceed independently.

1. **HTTP handler refines a pure request-to-response function.** For every byte prefix within the request buffer bound and every valid immutable site table, `handle` returns the reference outcome `NeedMore` or a response. A response consumes exactly the classified first request head and leaves its suffix for the next request unless the policy closes the connection. Its header prefix is the prescribed serialization. On a hit, GET serves exactly the selected entry, and HEAD emits no body with the same advertised content length as GET. Cover misses and each error result with their exact status and close behavior. Define the reference grammar over input bytes independently of parser result offsets. Prove acceptance and rejection against it, including a successful fixture for each supported method and a complete valid head followed by further bytes. [Parser](../src/Http.Parse.fst#L405) · [Handler](../src/Http.Server.fst#L1152)

2. **Public TLS steps refine a two-suite connection state machine.** Start at `init` and relate each reachable concrete state to explicit handshake and application states. A supported ClientHello with working crypto and sufficient capacities produces the modeled flight and waiting state. A complete valid client Finished for that exact flight establishes connection state with the modeled keys. Every reported application prefix then equals data authenticated in that direction and epoch. State which input is retained on incomplete records, which state changes on failure, and the exact records returned by sealing and closing. Prove both soundness and conditional progress for supported inputs. First strengthen the public wrappers to carry their existing helper postconditions, then connect the phase-1 C contract and fill in negotiation, credential, AEAD, and key-budget obligations. A concrete successful trace for each suite through Finished and the first application record makes the premises checkable. [State initialization and public API](../src/Tls.Conn.fst#L495) · [Flight composition](../src/Tls.Server.fst#L425) · [Finished evidence](evidence/aristotle-client-finished.md)

3. **The Rust shell preserves the connection's byte stream and the core's call invariants.** For every modeled sequence of partial reads, writes, and readiness events, the shell passes the correct prefixes to the core, preserves unconsumed suffixes, and counts each positive I/O result exactly once. Bytes written are a prefix of the modeled ordered responses or TLS records. On a fair execution with successful I/O and sufficient resources, complete supported requests receive their responses in request order until the specified close. Model both plaintext and TLS. In particular, the shell passes only the remaining space in its HTTP buffer to a TLS open, and the TLS core requires the whole application payload to fit there. A fragmentation theorem must account for that per-record constraint even when individual request heads fit the HTTP limit. Derive ABI preconditions at the actual call sites. [Shell I/O and response driver](../shell/src/main.rs#L197) · [Application buffer handoff](../shell/src/main.rs#L321) · [TLS delivery](../src/Tls.Conn.fst#L422) · [HTTP pipelining, RFC 9112 §9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)

4. **Boot and sandbox establish the site and capability invariants.** For a stable root under the stated filesystem policy, successful startup gives a well-formed immutable snapshot and identifies which file supplied each entry. After sandbox installation, demonstrate that newly acquired network descriptors come from the designated listener and enumerate which effects remain possible using inherited descriptors and the allowlist. Model failures of privilege dropping, sandbox setup, and resource allocation separately from successful startup. Prove the live-connection cap and a conditional idle-reaping bound as independent resource invariants. [Site loader](../shell/src/site.rs#L17) · [Startup and serving loop](../shell/src/main.rs#L385) · [Sandbox setup](../shell/src/sandbox.rs#L147)

5. **The refined TLS machine provides server authentication and application-data protection.** State peer agreement for an honest client that validates the configured server credential. For an active network adversary, require authenticated application delivery to correspond to a record sent by the matching peer in the same direction and epoch, with replay behavior implied by the sequence invariant. State application confidentiality separately, with an explicit observation model and security bound. Assume standard primitive security, an uncompromised certified server key, adequate entropy and the enforced per-key usage budget. Apply the theorem to the code through the functional refinement and faithful backend contracts. A code-level AEAD call relation by itself cannot justify those conclusions. [Current TLS proof scope](PROOFS.md#tls-13-srctlsfst) · [TLS key-usage limits, RFC 8446 §5.5](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.5)

6. **Selected native TLS paths satisfy a stated leakage contract.** For a fixed target and build, show that executions agreeing on public inputs and the permitted releases have the same modeled branch and address observations across secret values. Start with the Finished check and record protection, including success and rejection under the same public outcome. Define the declassification points and the treatment of decrypted record lengths before extending the property to the padding scan or the whole handshake. Keep microarchitectural timing evidence tied to the tested target. [Current timing and trace coverage](ASSURANCE.md#constant-time-checks)

On TLS, a proved public step relation and the shell stream relation would each mark concrete progress toward a server-level theorem. ## Reference relation for the shell proof

This is the proposed stream contract for `Connection::drive`. The public HTTP and TLS step contracts supply the abstract parser and record operations. The proof obligation is to relate each Rust call and each successful I/O operation to one step of this model. [Connection driver](../shell/src/main.rs#L229) · [Core ABI](../shell/src/core.rs#L68)

Let `read_wire` and `written_wire` be the concatenation of the byte prefixes returned by successful reads and writes on this socket. Let `accepted_wire` be the prefix submitted to and consumed by TLS input steps. Let `accepted_plain` be the concatenation of plaintext bytes returned by those steps, or `read_wire` for a plaintext connection. The invariants below apply up to the transition that starts shutting down or lingering on the socket. That transition classifies pending bytes as sent or discarded by the close policy. [Socket read](../shell/src/main.rs#L197) · [Shutdown handling](../shell/src/main.rs#L222)

- **Ingress.** For TLS, `read_wire = accepted_wire ++ pending_tls_input`. Each TLS step consumes a prefix of the pending bytes and appends only its application result to `accepted_plain`. An incomplete step preserves both pending input and the TLS state. For either transport, `accepted_plain = completed_heads ++ pending_http_input`, where `completed_heads` contains exactly the consumed request heads for retired replies in order. With a reply in flight, its head is a prefix of `pending_http_input` and remains there until the reply retires. [Request retirement](../shell/src/main.rs#L263) · [TLS input](../shell/src/main.rs#L321)
- **Egress.** The driver's active reply is one reference HTTP response, and its cursor is bounded by the length of its serialized header followed by its selected body. In plaintext mode, the cursor advances by exactly the bytes reported written. In TLS mode, it advances by bytes staged for sealing, and the pending wire record has a separate write cursor. For both transports, `written_wire ++ pending_wire_output` is the concatenation of bytes staged so far in reference order. TLS output includes the handshake, record protection, alerts and configured close behavior as defined by the core. Only a successful write advances the wire cursor. [Partial writes and TLS staging](../shell/src/main.rs#L243)
- **Progress.** Given fair readiness, positive I/O progress, successful allocation and faithfully implemented core contracts, a complete supported head receives its response and retires at the front of the queue. The hypothesis includes the documented request bounds, room for the complete application payload at each TLS input step, and any suite key budget. Malformed input, capacity exhaustion, EOF, fatal alerts and timeout are outcomes in the reference relation. They remain distinct from a successful authenticated close. [Response and close dispatch](../shell/src/main.rs#L263) · [TLS input and capacity](../shell/src/main.rs#L321) · [Timeout](../shell/src/main.rs#L344)
