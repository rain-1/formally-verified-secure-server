# What is actually proven (and what is not)

Everything below is machine-checked by `make verify` (F* + Z3) unless marked *tested* or *assumed*.

## HTTP core (`src/Http.*.fst`)

| Property | Status |
|---|---|
| Specification of request-target -> site key (`Http.Spec`): policy as local byte predicates | **spec** (human-reviewed) |
| Every key the spec can produce is well-formed: non-empty, only `[A-Za-z0-9._~-/]`, no empty segment, no segment starting with `.` (so no `.`/`..` component) — `Http.Spec.key_of_wf` | **proved** |
| `Http.Core.norm_key` computes exactly `key_of(path_of(target))` when the spec accepts the path, and rejects exactly when it does not | **proved** (functional refinement) |
| `Http.Core.lookup` returns an entry iff its key bytes equal the query key; entry offsets are bounds-checked | **proved** |
| Memory safety / no integer overflow / no out-of-bounds for parser, normalizer, lookup, header builder | **proved** (Low*) |
| Parser: accepted request => target lies inside the header block, `consumed <= input length` | **proved** |
| `Http.Parse.scan_headers` marks the request invalid when it reaches its line budget with headers still to scan. | **proved** |
| Successful `Http.Parse.parse` consumes a header section with at most 100 CRLF-terminated fields and a final blank line. Each field has a nonempty token name and a value made of visible ASCII, spaces, or tabs. Field name matching is ASCII case-insensitive. The section contains exactly one `Host`, rejects every `Transfer-Encoding` field, and permits only a single zero digit surrounded by optional spaces or tabs in each `Content-Length` field. `Http.Server.handle` carries the same guarantee for requests routed to a site entry or to 404. | **proved** |
| For a routed request, the close flag starts unset and is set exactly when any case-insensitive `Connection` field contains the ASCII substring `close` in its trimmed value, using case-insensitive matching. Subsequent fields preserve a set flag. The routing contract carries the flag through to the shell-facing result. | **proved** |
| `Http.Core.lookup` is also **complete**: "not found" means no in-bounds entry has the key | **proved** |
| `Http.Server.handle` routing theorem (`routed`): if it serves a body (`res[8]=1`) the body slice is the site entry whose key equals `key_of(path_of(target))` (target = the bytes the parser identified); if it answers 404 for a parsed request (`res[8]=2`) then either the path is rejected by the spec or no in-bounds entry has that key | **proved** |
| `Http.Server.build_header` serializes the status line, a canonical decimal `Content-Length` for its supplied 32-bit length, the `nosniff` field, `Allow` for 405, and the selected `Connection` field followed by a final blank line. A 200 response includes the exact `Content-Type` line selected for the supplied site key. The returned length is the length of the serialized header. | **proved** |
| `Http.Server.put_ctype` uses the suffix after the last dot in the final path segment. It matches the entire suffix against the media-type table using ASCII case folding. Missing, empty, and unknown extensions yield `application/octet-stream`. | **proved** |

| `Tls.Kdf.key_sched` preserves the live transcript while storing `derive_secret(handshake_secret(shared), "c hs traffic"/"s hs traffic", SHA-256(transcript))` and `master_secret(handshake_secret(shared))`. `tr_hash` hashes exactly the transcript prefix held in the state. | **proved** (relative to the assumption below) |
| `Tls.State.tr_add` succeeds exactly when the stored length plus the message length fits the transcript buffer. On success the transcript is the old prefix followed by the message bytes. On failure the heap is unchanged. | **proved** |
| `Tls.Kdf.install_keys` stores the derived AEAD key and IV for the selected suite and resets the sequence number to zero. `app_secret` stores the client application secret or installs server application keys derived from the stored master secret and transcript hash. `install_client_app` installs client keys from the stored client application secret. | **proved** (relative to the assumption below) |
| `Tls.Kdf.finished_mac` computes the RFC 8446 Finished verify_data for the supplied traffic secret and transcript hash. | **proved** (relative to the assumption below) |
| `Tls.Flight.build_sh` serializes the exact ServerHello handshake message for the supplied random, session ID, cipher suite, and X25519 share. The proof covers the handshake length, legacy fields, TLS 1.3 supported version, and all extension lengths. | **proved**. | `Tls.Server.emit_sh` preserves the supplied handshake bytes inside a TLSPlaintext record and emits a separate compatibility ChangeCipherSpec record when requested. The returned length covers exactly those records. | **proved**. [RFC 8446 §5.1](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.1) · [RFC 8446 Appendix D.4](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-D.4) |
| On success, `Tls.Server.hello_part` replaces the transcript with the received ClientHello handshake bytes followed by the exact ServerHello handshake bytes in the plaintext output. The transcript excludes the record headers and optional compatibility record. Both handshake traffic secrets derive from that transcript and the shared bytes returned by the X25519 binding. The master secret derives from the same shared bytes. | **proved** relative to the SHA-256, HMAC, and HKDF bindings. The X25519 binding has a memory-level contract. Finished relies on the SHA-256 and HMAC bindings below. | On success, `Tls.Flight.build_flight` writes EncryptedExtensions, Certificate, CertificateVerify, and Finished in that order. The transcript becomes its incoming bytes followed by exactly the returned flight. Finished authenticates the incoming transcript and the first three messages using the incoming server handshake traffic secret. The stored transcript hash covers the complete flight, including Finished. | **proved** relative to the SHA-256 and HMAC bindings below. [RFC 8446 §4.4.1](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.1) · [RFC 8446 §4.4.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.4) |

| `Tls.Flight.sign_cv` passes exactly the server CertificateVerify signing input to the P-256 binding. | Per-record nonce bytes equal the IV XOR the left-zero-padded sequence number. The sequence increment performs big-endian carry propagation and the sequence guard checks that the upper two bytes are zero. | **proved** |
| `Tls.Crypto.seal` and `Tls.State.send_rec` emit the TLSCiphertext header and model ciphertext/tag for the current write key and nonce. The same five header bytes are authenticated, and the plaintext passed to the AEAD is the content followed by its type. The write sequence advances on success. A zero length leaves the write state unchanged. | **proved** (relative to the AEAD bindings below). [RFC 8446 §§5.2–5.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.2) |
| `Tls.Crypto.unseal` and `Tls.Conn.open_rec` use the current read key, derived nonce, received header, and ciphertext/tag. An authenticated open yields the model plaintext and advances the read sequence. A rejected open leaves the connection state unchanged. The malformed-record result corresponds to an authenticated all-zero plaintext. A successful open identifies the last nonzero byte as the content type and the suffix as zero padding. | **proved** (relative to the AEAD bindings below). [RFC 8446 §5.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.4) |
| `Tls.Conn.check_cfin` reports success exactly when the supplied Finished verify_data equals the computed MAC. On success it installs the client application keys from the stored client application secret and resets the read sequence. `Tls.Conn.input` bounds consumed input, produced output and application bytes. It releases application bytes only in the connected phase and advances from waiting for Finished only on the successful encrypted-record path. | **proved** relative to the cryptographic bindings below. The public input contract still needs to carry the `do_ch` invariant through record opening and client Finished. |
| Memory safety, no overflow, buffer-disjointness discipline in every function (hello parser, key schedule, flight builder, record layer, state machine) | **proved** (Low*) |
| Bounds-checked ClientHello parser cannot read outside the record | **proved** |
| The **EverParse 3D** validator checks the ClientHello prefix against `spec/ClientHello.3d`. The grammar covers the version field, 32-byte random, session ID bounds, cipher-suite and compression vector lengths, and extension TLVs that exactly tile `extensions_len`. | **proved by EverParse's verification run**. The F\* binding assumes that the C adapter preserves the heap and returns either a matching prefix's end offset or an encoded error. |
| `Tls.ChValid.check` accepts only when the validator's end offset equals the full body length. A 32-bit length is below the encoded error range. Success from `Tls.Hello.parse` implies that the entire input body satisfies `Tls.ChValid.valid_body`. | **proved** relative to the validator binding. The binding interprets `valid_body` as a complete match of the local 3D grammar. |
| Full handshake transcript sequencing, CertificateVerify signature and DER encoding, and end-to-end handshake behavior | **tested** by interoperability (OpenSSL, curl, Python ssl; both suites; 300 KB transfers; mutated-input fuzzing under ASan/UBSan) |
| Cryptographic security of the protocol | **not claimed**. We rely on HACL*'s verified primitives and on RFC 8446's design; the composition here is unproved. |

## Assumed (trusted) interfaces

`src/Hacl.*.fst` and `src/EverCrypt.AEAD.fst` declare the contracts of the HACL*/EverCrypt C functions we call (`assume val`).
The SHA-256, HMAC-SHA-256, HKDF, and ChaCha20-Poly1305 bindings assume the C functions compute the corresponding vendored HACL* specifications. The AES-128-GCM binding uses abstract encrypt and decrypt operations for successful calls and associates the authentication-failure status with a model rejection. A concrete AES-GCM specification link remains open. X25519 and ECDSA P-256 have memory-level contracts.
Vendored C: `csrc/hacl` (commit `f557259007db9933442dde10aa995c1b00bd3446`); vendored F* specs: `third_party/hacl-fstar` (same commit, unmodified).

## Not verified at all

The Rust shell owns the epoll loop, socket I/O, timeouts, and site snapshot. Its FFI, descriptor-relative filesystem operations, and sandbox syscalls use trusted unsafe wrappers. Functional verification of the shell and its integration with the extracted core remains open. [Trust assumptions](TRUST.md)
